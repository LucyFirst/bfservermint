[ ] Evolution: the unit list icon stays on the old form until the next quest or a restart (added 30 Oct 2026)
    Reported: Lucy evolved Boxer Nemia (2*) -> Brawler Nemia (3*); Komik evolved Fire Beast Zegar (4*)
    -> Beast King Zegar (5*). After the evolution the unit list / evolve list / fusion list icon still
    shows the OLD form. Everything else is right: the unit's info page, sprite and stats show the new
    form, the admin page shows the new icon, and fusing into it works on the new unit. The icon only
    corrects itself after running any quest or restarting the app (the game then rebuilds its list).
    Cause (our reading): the game draws each list icon once and keeps it under the unit's own id
    (edy7fq3L). Our evolution keeps that id - like the official recordings do (UnitEvoRequest answer
    I82p0wCL: pn16CNah new id, edy7fq3L user unit id, t9FEW2KC old unit id, u1ECvfg8 user unit id
    before, dV3qji4I evolution type; both ids are the same in both recordings) - so the game reuses
    the cached picture. The app's UnitEvoInfo has setUserUnitIDBefore / setUserUnitID, so it is built
    to accept a NEW user unit id on evolution.
    Already tried (0971e1e): evolution answer no longer adds an empty "units added" list (qC2tJs4E)
    that the official answer doesn't have. Did NOT fix it.
    Possible fix: give the evolved unit a new user unit id (u1ECvfg8 = old id, edy7fq3L = new id) and
    move everything that points at the old id: the game's squads (party rows, all squads incl. trial
    teams), arena squad, raid squads (pl['raid']['squads']), equipped spheres (0R3qTPK9/RXfC31FA rows
    and the sphere storage rows that name the unit), favourite flag, 'Bvkx8s6M' (copy of the unit id
    inside the row), lord/type, imps, BB/SBB/SP levels (they live on the row, so copying the row covers
    them). Risk: a missed reference leaves an empty squad slot or a loose sphere. Test on Komik with a
    cheap evolution, in and out of a squad, with spheres on, before releasing.
    Decided 30 Oct: leave it (cosmetic, nothing lost). Workaround for players: run a quest or restart.

LDPLAYER ANDROID 14 FREEZES (2 Nov 2026)
    From about 1 Nov, the game on LDPlayer's Android 14 instances (PC 14.0.29.2 and a clean laptop
    install) freezes after a while on any screen (Manage Squad at once), and a fresh install stays
    black after sign-in. Phones (Wi-Fi or mobile data) are fine; the server logs no errors and the
    game sends nothing before freezing (stuck in the game's own code under LDPlayer's ARM
    translation). An LDPlayer Android 9 instance works - use that.
    CONFIRMED: it starts at a fixed moment, between 15:30 and 16:30 UTC on 1 Nov 2026 (midnight
    Singapore time). Emulator clock 1 Nov 08:30/09:30/15:30 UTC = fine; 16:30 UTC, 8 Nov, now = freeze
    (log in, Units / Manage Squad). Not the local date (Honolulu time zone, local 1 Nov, still froze),
    not the US clock change, not Mondays. Server traffic identical in a good and a frozen run; nothing
    in saves/admin_settings ends at that moment. Next: narrow to the minute (15:45/16:00/16:15 UTC),
    then find the code in libgame that compares against it. Tools: SET-DATE.bat MMDDhhmmYYYY (UTC),
    SET-CLOCK-NOW.bat (Komik's window, port 5559).
    FOUND (armpc5 snapshots, 2 Nov): the stuck thread loops in libgame FileLoader -
    processSamAndCutSceneFile (0x1cd9bc0) -> downloadBundlePriority / addLoadFilePriority ->
    specialSamHandler (0x1cd8168, string search memchr/memcmp in LDPlayer's ARM libc). It is the
    per-frame "downloaded files to process" pass. Game prefs (gamedata.xml) hold a pending
    reload_files list 3105-3134 (F_RELOAD_FILE_MST rows: layout csvs, unit cgg/cgs, 2020-21 banners).
    Still to find: what the 16:00 UTC moment changes in that pass. Then patch libgame (1.0.8).
    Tools: GET-ARM-PC-5.bat (40 snapshots), GET-GAME-PREFS.bat (copies the game's saved settings).
